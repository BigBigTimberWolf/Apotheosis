# 新马克（新 MAKCU）不启动 —— 根因与修复

## 结论（一句话）

右板的 `memory_type` 是 `qio_qspi`，让 app 以 **QIO** 读模式初始化 flash；新板子上的
GD25Q32E 写 QE 位失败，而 QIO 属于 quad 模式、失败**不被容忍**，于是
`esp_flash_init_default_chip()` 静默返回错误 → `do_core_init` 断言 → 无限重启。
改成 **DIO** 读模式就正常了。

改动只有一个字段：

```jsonc
// fw_host_kbd/boards/MAKCM.json
"arduino": {
  "memory_type": "dio_opi"     // 原来是 qio_qspi
}
```

---

## 症状

| | 现象 |
|---|---|
| 串口（COM9） | `assert failed: do_core_init startup.c:328 (flash_ret == ESP_OK)`，每秒重启几十次 |
| 键盘 | 完全没反应（右板根本没跑起来） |
| 官方固件 | 同一块板子**正常**（所以板子是好的） |
| 旧马克 | 我们这份固件**正常**（所以固件逻辑是好的） |

关键点是：**崩在任何我们自己的代码之前**，而且**没有任何可读的错误日志**。

---

## 排查过程（走过的弯路，供以后参考）

先说三条被实测**证伪**的假设，避免以后重复踩：

1. ~~"镜像头声明 4MB 比实际大，容量检查失败"~~
   实测 `esptool flash_id`：`Manufacturer c8 / Device 4016 / 4MB`，芯片就是 4MB。
   而且声明改成 2MB 之后**断言依旧**，重启次数从 31/6s 变成 31/6s —— 完全没变。

2. ~~"烧了 USB_PHY_SEL eFuse"~~
   那支函数有 `already_burned` 早退，而且官方固件已在这块板上跑过 —— 早烧过了。

3. ~~"官方 repo 里的 partition CSV 就是发布固件的布局"~~
   不是。从 `V3.4_RIGHT.bin` 的 `0x8000` 直接解析出来的才作数。

### 真正定位到机制的三步

**第 1 步：确认断言位置和它的真实语义。**

从 IDF 源码 `esp_system/startup.c`：

```c
esp_flash_app_init();
esp_err_t flash_ret = esp_flash_init_default_chip();
assert(flash_ret == ESP_OK);          // 第 328 行，就是它
```

**第 2 步：读 `esp_flash_init_main()`，找出静默返回路径。**

`components/spi_flash/esp_flash_api.c` 里，这个函数有**三条不带任何日志**的错误返回：

```c
err = esp_flash_read_chip_id(chip, &flash_id);
if (err != ESP_OK) return err;              // ← 静默 1
...
err = detect_spi_flash_chip(chip);
if (err != ESP_OK) return err;              // ← 静默 2
...
err = chip->chip_drv->set_io_mode(chip);    // ← 静默 3（最后一句）
if (err == ESP_ERR_FLASH_NO_RESPONSE && !esp_flash_is_quad_mode(chip)) {
    err = ESP_OK;        // ★ 只有【非 quad】模式才容忍 QE 位设置失败
}
```

`set_io_mode` 内部只打 `ESP_EARLY_LOGD`，而预编译 SDK 库里这个级别被裁掉了 ——
所以整条路径在串口上**一个字都没有**。这就解释了为什么日志里只有断言、
却看不到任何 "spi_flash" 的报错。

**第 3 步：找到 `read_mode` 从哪来。**

`components/spi_flash/esp_flash_spi_init.c`：

```c
#if defined(CONFIG_ESPTOOLPY_FLASHMODE_QIO)
#define DEFAULT_FLASH_MODE  SPI_FLASH_QIO
#elif defined(CONFIG_ESPTOOLPY_FLASHMODE_DIO)
#define DEFAULT_FLASH_MODE  SPI_FLASH_DIO
#endif
...
static esp_flash_t default_chip = { .read_mode = DEFAULT_FLASH_MODE, ... };
```

`read_mode` 是**编译期常量**，而 `CONFIG_ESPTOOLPY_FLASHMODE_*` 由 SDK 变体决定，
变体又由 board json 的 `build.arduino.memory_type` 决定。

### 静态证明（刷机前就拿到了证据）

每个变体有**自己的** `libspi_flash.a`（不是六变体共享），所以改 `memory_type`
真的会改变产物。把 `esp_flash_spi_init.c.obj` 抽出来对比：

| 变体 | 该 obj 的 SHA256 | `default_chip.read_mode` |
|---|---|---|
| `qio_qspi` | `D9035B4D…` | **0x05 = QIO** ← 会挂 |
| `dio_qspi` | `AAAF0C1C…` | **0x03 = DIO** ← 正常 |
| `dio_opi`  | `AAAF0C1C…` | **0x03 = DIO** ← 正常 |

（`read_mode` 在 `esp_flash_t` 结构体偏移 `0x10`。）

修好之后再从**链接后的 ELF** 里读一次 `default_chip`（地址 `0x3FC94B8C`，
位于 `.dram0.data`），确认字段真的是 `0x03`：

```
32 字节: ac 4b c9 3f 00 00 00 00 08 4c c9 3f 00 00 00 00 03 00 00 00 ...
                                                          ^^ read_mode = DIO
```

## 为什么官方固件没事

官方发布固件（`V3.4_RIGHT.bin`）的二级 bootloader 是 **13800 字节 / 入口 `0x403c8878`**，
而 SDK 预编译的四个 bootloader 转出来都是 **15096 字节 / 入口 `0x403c98d0`** ——
**官方用的是另一套 / 更新版本的 arduino-esp32**，其 flash 驱动能正常处理这颗
GD25Q32E 的 QE 位。我们这份基于 arduino-esp32 2.0.16 (IDF 4.4.5) 的构建不行。

也正因为这样：**旧马克能用**（那颗 flash 的 QE 位写得进去），**新马克不行**。

## 修复后选哪个变体

| 变体 | flash | PSRAM | IGNORE_NOTFOUND |
|---|---|---|---|
| `dio_qspi` | DIO | QUAD | 无 |
| **`dio_opi`（选用）** | **DIO** | **OCT** | **有** |
| `qio_qspi`（原来） | QIO | QUAD | 无 |

选 `dio_opi` 的理由：它把**真正要改的那一个轴（flash 读模式）改成 DIO**，
同时对 **PSRAM 类型免疫** —— `IGNORE_NOTFOUND` 让 PSRAM 找不到时也不会 abort。
这份键盘固件不用 PSRAM，所以最坏情况只是 PSRAM 不可用，但**一定能启动**。

（左板固件 `fw_device_kbd` **不要动**：它现在跑 `qio_qspi` 在新马克上是正常的，
说明左板那颗 flash 吃得下 QIO。能跑就别改。）

## 验证结果

| 检查项 | 修复前 | 修复后 |
|---|---|---|
| COM9 里 `assert failed` | 每 6 秒 31 次 | **0** |
| COM9 里 `rst:0x` 重启 | 每 6 秒 31 次 | **0** |
| COM9 设备（USB-Serial-JTAG） | 一直在 | **硬复位后消失** |
| 左板 `km.version` 应答 | `MAKCU-PASSTHROUGH-1.0.0` | 不变 |

最后那一项是关键证据：ESP32-S3 的 **USB-Serial-JTAG 和 USB-OTG 抢同一对
GPIO19/20**。硬复位后 COM9 从 `Present=True` 变成 `Present=False`，
说明 **app 真的跑起来了，并且 `usbHost.begin()` 已经接管 USB 口进入 Host 模式**。
不是"卡住了"，是真的在正常工作。

## 刷机产物

- `【键盘版_右板_DIO修复】.bin` —— 665008 字节
  - bootloader 头 `e9 03 02 1f`：DIO / 80MHz / 2MB
  - 分区表：`nvs 0x9000/0x6000, phy_init 0xf000/0x1000, app0 0x10000/0x100000,`
    `coredump 0x110000/0x10000, storage 0x120000/0x40000`（最高 0x160000 = 1.38MB）
    —— 与官方 `V3.4_RIGHT.bin` 完全一致
  - 刷写：`esptool erase_region 0x0 0x10000` + `write_flash -z 0x0 <bin>`

## 两个附带修好的坑

1. **`scripts/merge.py` 的 `IndexError`**：`csv.reader` 遇到空行会返回**空列表**，
   而代码直接取 `row[0]` → `IndexError: list index out of range`，整个构建失败。
   已加空行/注释行保护。

2. **分区 CSV 必须纯 ASCII**：PlatformIO 的 `checkprogsize` 用系统代码页（本机 GBK）
   读这个文件，中文注释会以
   `UnicodeDecodeError: 'gbk' codec can't decode byte 0xa8` 直接崩构建。

## 还没验证的一步

右板现在是好的，但**键盘要插到右板的 USB-C 上**才能验证整条链路
（刷机时那个口被电脑占着）。测试步骤：

1. 把**右板 USB-C 上的电脑线拔掉**，换成真键盘接收器
2. 左板 USB-C 接到目标电脑
3. 按键盘，目标电脑上应该有输入

如果还是不行，下一步就该把左板刷成**带诊断**的版本
（`【键盘版_左板_带诊断】.bin`），这样 COM5 上会有 1Hz 的
`[KBD-RIGHT] kbd=… mouse=… iface=… reports=… frames=… id=…` 心跳，
可以一眼看出右板到底读到没有。
