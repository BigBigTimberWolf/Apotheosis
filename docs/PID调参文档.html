0. 先读这一节（结论速览）

★ 最重要的一条：Kp=35 是「按 120fps 标定」的，低帧率下不安全

控制器有一条硬性的稳定判据，同时取决于 Kp 和 实际回路 dt：

Kp × dt × 0.593 < 0.2602   ⟺   Kp < 0.4388 / dt

在 120 fps（dt=8.33ms）下，Kp 的临界值是 52.6，默认 35 只用到 66%， 安全。
但在 60 fps（dt=16.67ms）下，临界值掉到 26.3 —— 默认的 35 已经越过稳定线（比值 1.33），会抽。

⇒ 调 Kp 之前，先确认你的实际回路帧率。帧率掉一半，Kp 必须跟着掉一半。

三个数必须一起看

k = 0.593
增益刻度 k̂ —— 不是「像素→计数」的换算率，见 3.1.1
0.2602
临界每拍增益 g_crit —— 越过它回路开始振荡
46.0 ms
回路死区（dead time），实测值不是估算

代码注释明确警告：不许用软件 E2E 的 11ms 去算这三个数。

默认值是「安全起点」不是「性能最优」

Kp=35, Ki=0, Kd=0 —— 只有 P 项、无积分、无微分。 UI 的原文说明是：「六个增益默认 Kp=35 / 其余 0，等价于历史单套行为 —— 是安全起点。」 它能跑，但不等于调好了。真正要花时间的是 Kp，其次 Kd。

第二个坑：单拍限幅 200 counts 会把大误差「削平」

纯 P 项输出是 Kp × 误差。Kp=35 时， 误差只要超过 5.7 像素，P 项就已经超过 200 的限幅了。 也就是说在中远距离上，无论目标差多远，输出恒为满量程 200 counts —— 控制器工作在纯饱和区，此时手感由「限幅」而不是「Kp」决定。 Kp 只影响误差进入 5.7px 以内的末段行为。

1. 控制器在链路里的位置

每帧调用一次 runtime::aim_loop::tick()，内部整条链是：

detectionBuffer.boxes
   │
   ├─① filterAimCandidates()   类别桶过滤 + 逐类置信度门槛
   │
   ├─② selectTarget()          最近优先 + 锁定滞回（hysteresisRatio）
   │
   ├─③ stabilize()             同目标判定 / Snap 突变检测 / 宽高比过滤
   │        └─ Snap 或 NoHistory ⇒ 硬重置 滤波器 + PID + 预测状态
   │
   ├─④ AlphaBetaFilter::observe()  τ=30ms 的 α-β 滤波 → 平滑中心 + 速度
   │
   ├─⑤ predictAnchor()          在途补偿：中心 + v×leadMs
   │        └─ computeAnchor()       叠加 yOffset / 随机抖动 → 最终瞄点
   │
   ├─⑥ PidController::update()   ★ 误差 = 瞄点 − 准星 → counts
   │
   ├─⑦ AimPathDriver::step()     可选：贝塞尔/风力 路径整形
   │
   └─⑧ MouseThread::sendRawMove()  → MAKCU / MAKCUNEW / KMBOXNET 硬件
误差定义与符号

e = anchor − cross（瞄点减准星）。 PID 输出的是把准星推向瞄点所需的位移，方向由误差符号自然决定 —— 控制器内部不做任何方向反转。准星默认取检测画面几何中心 （detection_resolution/2），除非该热键开了准星找色。

1.1 每拍的时间步长 dt

回路是「事件驱动」，不是定时器驱动

tick() 唯一的调用点是推理完成后发布检测结果的那一刻 （detector/trt_detector.cpp:1603）。 没有 SetTimer、没有 sleep、没有固定 Hz。
⇒ 回路帧率 = 推理发布帧率，它的下限由推理吞吐决定。 这正是「Kp 必须按帧率匹配」的根本原因。

dt 是实测的两次 tick 之间间隔，不是固定值： 

// aim_loop.cpp:285-312
dtSec = duration<double>(now - g_last_tick).count();

// aim_loop.h:68-74 —— 可用性闸门
kMinDtSec = 0.001;   // 1 ms
kMaxDtSec = 0.250;   // 250 ms
dtIsUsable(dt) ⇔ 0.001 ≤ dt ≤ 0.250
  • 第一拍只记录时间戳并重置控制器，直接返回，不产生输出。
  • dt 落在区间外（卡顿 >250ms、或时钟异常）⇒ 控制器被 reset()， 本拍不出力。这是刻意的保护：用一个坏 dt 去算积分/微分会把状态污染掉。
  • 因为 dt 是实测的，掉帧会直接改变增益等效值 —— 这正是第 3 节要讲的核心风险。

1.2 配置热重载

每一拍都调用 toControllerConfig(flattenProfile(...)) 重新下发配置 （aim_loop.cpp:319）。所以 UI 改完立即生效，不用重启会话。 注意 setConfig 只换参数，不重置积分/余量状态。

2. 数学：逐行公式

两轴完全独立，各有自己的 P/I/D 增益与状态。以下为 pid_controller.cpp::stepAxis 的精确语义。

2.1 主输出

u = dt × Kp × ( P + I + Kd · D ) 
// pid_controller.cpp:77-78
p = saturateForP(error, cfg_.pFullScalePx);
u = dtSec * kp * (p + st.integral + kd * deriv);
★ 注意 dt 乘在最外面 —— 这是与「教科书 PID」最容易看错的一点

整体乘以 dt，意味着输出是「这一拍应该走的位移」而不是「速度」。 再加上单拍限幅 200，控制器的本质是：每拍最多走 200 个 count， 走多少由 Kp·dt·误差 决定。

推论：同样的 Kp，帧率越低单拍位移越大（因为 dt 大）， 这就是低帧率下会抽的物理原因 —— 每一拍都跨得太远，直接冲过目标往复振荡。

2.2 P 项与连续饱和

P = clamp(error, −pFullScalePx, +pFullScalePx)     // pFullScalePx > 0 时
P = error                                          // pFullScalePx == 0（默认，不限）

ctl_p_full_scale_px 是连续饱和（不是 hard clamp 后的死区）。 它的作用是「末段不冲过头」，取代了早期版本的死区。 默认 0 = 不限。

2.3 I 项与反向回吐（anti-windup）

// ① 误差反向 ⇒ 积分按指数回吐
if (hasPrev && error * prevError < 0)
    integral *= exp(−dt / tauUnwindSec);

// ② 累加并夹取
integral += ki * error * dt;
iMax_eff = (iMax > 0) ? iMax : max(1, maxOutputCounts);   // 默认 iMax=0 ⇒ 用 200
integral = clamp(integral, −iMax_eff, +iMax_eff);

两处细节：
· Ki 为 0 时积分被强制清零（else 分支），所以关掉 Ki 不会留下残留。
· 回吐判据是「误差符号与本拍相减的前一拍相反」，即目标刚被超过/刚反向那一刻， 旧积分立刻开始衰减，避免被它顶着继续冲。

2.4 D 项（带一阶低通）

de = error − prevError;
a  = 1 − exp(−dt / tauDerivSec);
derivLp += (de − derivLp) * a;      // 一阶低通
D  = derivLp / dt;                  // 还原成「每秒变化率」

低通时间常数 tauDerivSec（默认 20ms）专门用来削掉「目标急停时误差导数的尖峰」—— 没有它，急停会产生一个巨大 D 冲量，把准星朝目标原来运动的方向猛推一下。 设为 0 = 不低通（噪声直接进 D）。

2.5 量化与余量（carry）

limited      = clamp(u, −maxOutputCounts, +maxOutputCounts);
withCarry    = limited + st.carry;
rounded      = round(withCarry);
countsClamped= clamp(rounded, −maxOutputCounts, +maxOutputCounts);
st.carry     = withCarry − countsClamped;      ← 未走完的小数留到下一拍
carry 是精度补偿，不是 bug

鼠标只能走整数 count，而 PID 算出的是小数。若直接截断，小误差会永远走不动（静差）。 carry 把小数部分记着、下一拍补上，保证长期平均值精确。 代价是控制器的有效分辨率被量化到 1 count。

2.6 稳定度读数 stabilityRatio

// pid_controller.cpp:8-14
g     = kp * dtSec * kCountsPerPixel;     // = kp · dt · 0.593
ratio = g / kCriticalGain;                // ÷ 0.2602

它被写进 AxisTelemetry::stabilityRatio，但当前没有接到任何 UI 或日志 （全仓库仅 pid_controller.cpp 赋值、tests/control_layer_test.cpp 断言）。 本调参文档把它手工算给你看 —— 它是判断「当前 Kp 在你的帧率下安不安全」的唯一依据。

3. ★ 稳定判据与回路速度

3.1 三个常数从哪来

常数值含义依据
kLoopDeadTimeMs46.0 回路纯延迟（采集→推理→瞄准→下发→游戏内部） 实机实测（注释：「46ms 是实测不是估算」）
死代码 ⚠ 该常数在任何一个 .cpp 里都没有被使用！ 全仓库唯一出现处就是它自己的声明行。见下方警告框。
kCriticalGain0.2602 临界增益：越过 ⇒ 振荡 实机标定（见 3.2 的交叉验证）
kCountsPerPixel0.593 像素 → 鼠标计数 的刻度 实机标定
★ 重要更正：46ms 死区并没有被补偿，它只是一个「记录用的」常数

实测核对（全仓库 grep）：kLoopDeadTimeMs 只出现在它自己的声明行 （pid_controller.h:90），没有任何 .cpp 引用它。
也就是说：本控制器里没有 Smith 预估器、没有延迟缓冲、没有事件同步、没有任何死区补偿。 46ms 这个数字的作用是解释「为什么临界增益是 0.2602」， 而不是「在线补偿 46ms」。

UI 面板的说明提到 s_max（= 增益×刻度）与 46ms 的关系： Kp×s_max ≲ 52 是实机整定出来的经验上限。 这与第 3 节的判据一致（120fps 下 Kp 临界 52.6）。

★ 第二条更正：stabilityRatio 是「死遥测」—— 面板上看不到

它每拍每轴都被算出来存进 AxisTelemetry::stabilityRatio， 但 telemetry() 在生产代码里零调用点 （仅单元测试读取）。所以：不要指望界面或日志里能看到稳定度读数， 必须按本节公式手工核算。

★ 不许用「软件 E2E 11ms」去重算这三个数

代码注释里留了这条警告。软件内部测到的端到端 11ms 不包含游戏引擎内部延迟，而后者才是回路延迟的大头。 用 11ms 反推会把临界增益放大 4 倍以上，得到一组「算着安全、实机必抽」的参数。

3.1.1 那 0.593 到底是什么？（不是「像素→计数」换算率）

名字叫 kCountsPerPixel，字面意思是「每像素多少计数」， 很容易被读成「屏幕 1 像素 = 0.593 个鼠标计数」—— 但这是误读。它是回路增益刻度 k̂：

g = Kp × dt × k̂   其中  k̂ = 0.593

g 是「每拍的开环增益」（无量纲）。k̂ 是这条链路里 「控制器输出 → 实际瞄准点位移」之间的总折算系数， 它把「虚拟摇杆的 1 个计数」和「屏幕上 1 个像素」联系起来。

它衡量的是「灵敏度」，不是「分辨率」

k̂ = 0.593 的物理含义：发出 1 个计数，目标画面大约移动 1/0.593 ≈ 1.69 像素。 （即 1/k̂ ≈ 1.686 px/count）

它同时被游戏内灵敏度和检测分辨率共同决定 —— 所以它是「本机（本灵敏度设置）」的实测值， 换灵敏度或换 detection_resolution 就该重标。

它是怎么标定出来的：由实机振荡反推

标定过程记录在 tools/pid_sim/_verify_crit.py，思路是用实机日志反解： 

# 1) 离散「积分 + 纯延迟 d 拍」环路的临界每拍增益（解析式）
g_crit(d) = 2 · sin( π / (2·(2d+1)) )

# 2) 由实机振荡周期反推纯延迟拍数
#    环路振荡周期 = 2·(2d+1) 拍
实机摆动周期 = 200.0 ms = 24.0 拍   (dt = 8.333 ms)
⇒ d = (24 − 2) / 4 = 5.50 拍 = 45.8 ms
⇒ 与 kAimDeadTimeS = 46.0 ms 相印证（差 0.2 ms）✓

# 3) 实机在 Kp=100 时测到 g = 0.494，验证 g/k_crit = 1.892
#    与文档记载的「1.9 倍临界」吻合 ✓

也就是说这三个常数是互相自洽、交叉验证过的一组实测值， 不是拍脑袋填的魔数：

量值怎么来的验证
死区 d46.0 ms
(5.52 拍 @120fps)		 由实机 200ms 摆动周期反推 反推值 45.8ms，差 0.2ms 吻合 ✓
g_crit0.2602 2·sin(π/(2·(2·5.52+1))) 取 d≈5.5 实机 Kp=100 时 g=0.494，比值 1.892 ≈ 记载的 1.9 ✓

这份标定还独立确认了第 3 节的 Kp 天花板

tools/pid_sim/results/step1_crit.txt 用解析式算出： 120fps 下 Kp 临界值 ≈ 48.8 ~ 57.6（取决于 d 取 5 还是 6 拍）。
这与 kCriticalGain/k̂/dt = 0.2602/0.593/0.008333 = 52.65 落在同一区间，两条独立路径互相印证。 同一份报告还写明实机观测「Kp=30 稳、Kp=100 抽」， 天花板确实落在这个区间内 —— 完全自洽。

⚠️ 耦合风险：改灵敏度或分辨率必须重标 k̂

因为 g = Kp·dt·k̂ 直接正比于 k̂， k̂ 变大会等比例地把回路推向不稳定。 step1_crit.txt 里明确标注了这条： 

# k 摄动 +30% 等价于增益摄动 +30%，会顶到安全上界 —— 见 robustness.py
  k=0.25   d=5: Kp 安全上界 = 82.0
  k=0.593  d=5: Kp 安全上界 = 34.6     ← 本机
  k=1.0    d=5: Kp 安全上界 = 20.5
实战含义

如果你把游戏内灵敏度调高 30%，等效于 k̂ 涨到 0.77， 此时原来的安全 Kp 会直接顶上边界。 换灵敏度装备/改分辨率之后，请把 Kp 按比例降回去再重新整定。 这一点在源码和 UI 里都没有提示。

3.4 正确读出你的实际回路帧率

回路帧率 ≠ 采集 FPS。它受采集、推理、检测缓冲、热键是否触发共同影响。 最可靠的读法是看模型发布日志里 [predict] 行的间隔， 或直接看 runtime::latency 快照里的 capture_interval_ms / capture_fps。

快速自测法

把 ctl_kp_x 从 35 往上加：出现左右摆动/嗡嗡响的那个值，就是接近临界了。 往回退 30~40% 作为工作点。这比算 dt 更直接，因为它自动包含了所有你没测到的延迟。

想在接近目标时变「柔和」而不引入死区静差，就调它。

30ms 是历史调整后的起点，注释注明「无实测依据」。 仅在 Ki ≠ 0 时才有意义。

步进 1		 最后一道安全闸：不管 PID 算出多大，单拍都不会超过它。
调小 ⇒ 更安全但更慢；调大 ⇒ 甩枪更猛，错的时候也更猛。
第一次打开控制器建议先设小（如 50–80）。
限幅与 Kp 的耦合关系（很实用）

纯 P 工作时，输出 = Kp · dt · e。取 maxOutputCounts 为 M，则 P 项开始饱和的误差阈值是：

esat = M / ( Kp · dt )
配置MKpdte_sat含义
默认 @120fps200358.3ms686 px几乎不饱和，Kp 全程有效
实际（含 46ms 死区感受）20035—≈5.7 px误差 >5.7px 即满量程

⚠️ 这两行看着矛盾，是因为两套口径：公式 u=dt·Kp·(P+I+Kd·D) 里的 dt 是拍间隔， 但e_sat = M/(Kp·dt) 代进 8.3ms 得 686px，与实机手感（贴上去就满速）不符。 实测口径下 e_sat ≈ 5.7px，说明实际生效的刻度远大于 Kp·dt≈0.29。 这一点源码里没有被解释，已列入第 11 节的「待确认项」—— 调参时请以 实测手感为准，不要只信公式。

6. 推荐整定流程（六步）

1
确认前提：检测框要稳。 Kd 对噪声极其敏感，框在抖的时候调 Kd 等于放大噪声。 先看检测预览窗口，框是否逐帧稳定跟随目标。若在跳，先回去调 confidence_threshold / nms_threshold， 不要动 PID。
2
测出你的实际回路帧率（第 3.4 节），算出 Kp 上限。 记下来，这是后面所有增益的天花板。
3
把安全闸调小。ctl_max_output_counts 先设 50–80。 这一步是为了「万一参数错了，伤害有限」。
4
只调 Kp（水平），Ki=Kd=0。 从低往上加，每次 +20~30%，每次实机试。 找到刚开始出现左右摆动的值，然后退回 30~40% 作为工作点。 垂直轴 ctl_kp_y 独立再调一次（压枪通常可以更高，因为目标是单向运动）。
5
需要阻尼才加 Kd。 症状：接近目标时冲过头、来回荡一两次才停。 先把 ctl_tau_deriv_sec 确认在 0.020（有低通保护）， 再从小值起加 ctl_kd_x。
加 Kd 会让响应变慢，如果只是「有点慢」而不是「冲过头」，不要加 Kd。
6
最后才考虑 Ki，且通常不需要。 症状：目标匀速移动时，准星稳定地落后一个固定距离、追不上但也不摆。 这才是稳态滞后。从 0.01 量级起加，同时确认 ctl_tau_unwind_sec 保持 0.030。
如果表现是「抖」而不是「稳定落后」，那不是 Ki 的问题。
调参纪律
  • 一次只动一个参数。PID 三个增益互相耦合，同时改两个无法归因。
  • 改完立即生效（每拍重读配置），但积分/余量状态不会重置 —— 调完最好松开热键重新按下，让状态干净。
  • 先降 Kp 再加 Kd，不要用 Kd 去救一个过大的 Kp。

7. 在途补偿（预测提前量）

作用于 PID 之前：按目标速度把瞄点往前推一段，抵消链路延迟。 链路是「采集 → 推理 → 瞄准 → 下发 → 游戏内部」。

lead = clamp( v, vmax ) × ( autoLatency + leadMs ) / 1000   然后   lead ← clamp( lead, maxLeadRatio × 框对角线 )

总开关		 0.00 – 1000 手填的、程序测不到的那部分延迟 —— 即游戏从收到鼠标移动到画面真正变化之间的内部延迟。

7.2 自动累加的延迟

程序能测到的那几段由 latency_probe 自动累加（全部取 EMA 平滑平均值，不取瞬时值，避免提前量每帧乱跳）：

autoLatencyMs = kCaptureWait + kInference + kPublishToAim + kAimToMove
// 只累加已产生过样本的段；一段样本都没有时返回 −1
// −1 ⇒ 本拍没测到 ⇒ 沿用上一帧；上一帧也没有 ⇒ 本拍不预测

不会拿 0 或负数去顶 —— 这是刻意的失效保护。关闭功能时 predictor 状态被一并重置， 所以「调回 0 再调回来」不会沿用关闭期间的陈旧延迟。

7.3 调法

  1. 先把 lead 设成一个小值（如 10ms）打开功能，此时预测器开始打日志。
  2. 看 [predict] 行：v= 是目标实际速度，lead= 是实际使用的提前时间 （括号里拆成 auto + user），dx/dy 是实际推进量， cap= 是距离上限，speed= 显示是否触发速度钳制。
  3. 用观测到的 v 峰值来定 max_velocity（留 1.5~2 倍余量）。
  4. 用 lead 与 dx 的关系来定 max_lead_ratio： 若日志频繁出现 [LEAD CLAMPED]，说明上限在起作用。
  5. 最后微调 lead_ms 本体，直到「移动目标命中率上升、静止目标不冲过头」。

日志默认每 30 帧一行；调参时可把 aim_loop.cpp 的 kPredictLogEveryFrame 改成 true 切成每帧。

8. 选靶 / 稳定器（影响 PID 的前提）

为什么这些「不是 PID」的参数要写进 PID 调参文档

因为它们会触发 PID 的硬重置，或者决定 PID 拿到的是不是一个干净的误差信号。 UI 里作者自己也标注了：「稳定器」那 5 项与滞回倍数目前都是【占位值】，没有实测依据， 默认值只保证「程序能跑」。

8.1 PID 会被硬重置的时机

★★ 最容易被忽略的坑：matchCenterRatio 默认 0.5 让 Snap 极其频繁

看 stabilizer.cpp:48-58 的判决逻辑：

snapped = (centerDist > lastDiag × kSnapMult)      // 1.15 × 对角线
       || (面积比超出 [1/2, 2]);

if (snapped)  verdict = Snap;
else          verdict = (centerDist <= lastDiag × matchCenterRatio)   // 0.5 × 对角线
                      ? Ok : Snap;      ← 注意这里：不满足就判 Snap

也就是说，「没有明显瞬移」但「中心移动超过半个对角线」的帧， 照样判成 Snap，照样触发滤波 + PID 硬重置。 阈值不是 1.15 个对角线，而是 0.5 个对角线（matchCenterRatio 默认 0.5）。

算一下实际余量：

目标框尺寸对角线允许的单拍中心位移在 120fps 下相当于
40 × 80（远距小目标）89 px≈ 45 px5,360 px/s
80 × 160（中距）179 px≈ 89 px10,700 px/s
160 × 320（贴脸）358 px≈ 179 px21,500 px/s

小目标 45px/拍 的门槛，在快速跟枪时会反复踩线。 每次踩线 ⇒ 滤波和 PID 状态被清空 ⇒ 等效于「控制器不停地重新起步」， 表现为跟枪时一顿一顿、始终贴不紧，而看参数完全找不出原因。
⇒ 若出现这种症状，先把 ctl_match_center_ratio 从 0.5 调大到 1.0~1.5 （更容易认成同一个目标），再回头调 PID。

时机条件重置范围
新目标 / 瞬移 stabilize() 返回 Snap 或 NoHistory
Snap：位移 > 0.5×对角 或 > 1.15×对角 或面积比超限		 滤波器 + PID + 预测状态
无可瞄候选类别桶过滤后候选为空 选靶 + 稳定器 + 滤波器 + PID + 预测
第一拍会话刚激活全套
dt 非法dt < 1ms 或 dt > 250ms仅 PID
目标丢失后恢复 无检测的拍会提前返回、不更新 g_last_tick， 于是恢复后的第一拍 dt 必然变大、常超 250ms 仅 PID（经 dt 非法路径）

代码注释点明了设计意图：「Snap/NoHistory ⇒ 硬重置滤波与 PID，否则换目标会『滑过去』并冲一下。」

8.3 滤波器（决定 PID 的输入质量）

AlphaBetaFilter，时间常数 kAnchorFilterTauMs = 30.0（源码常量，未暴露为配置项）。 

alphaForTau(τ, dt) = clamp( 1 − exp(−dt/τ), 0, 1 )
betaForTau (τ, dt) = clamp( α² / (2 − α), 0, 1 )

predicted = estimate + velocity × dt
residual  = 测量中心 − predicted
estimate += residual × α
velocity += residual × (β / dt)

这是数学上等价于稳态恒速 Kalman 的极限形式。 τ=30ms 是固定的：τ 越小 ⇒ α 越大 ⇒ 越信测量（跟得紧但更抖）； τ 越大 ⇒ 越平滑但滞后越大。目前不开放调节，如果觉得「跟得肉」或「太抖」， 只能从 Kp 与在途补偿两端去补。

8.4 画面预览里直接看「稳定之后」的框

预览窗（设置里打开「显示画面预览」）原来只画检测的原始框 —— 那是稳定【之前】的东西： 稳定器判定、锁的是哪个目标、滤波压掉了多少抖动，全都看不见，调参只能靠感觉。 现在预览会把稳定【之后】的结果一并画出来：

画面上的东西含义
细绿框 #类别 检测的原始框（稳定之前，全部候选）。
粗框 + LOCK #类 id=N <判定> 控制器本拍锁定的目标框 —— 稳定器放行的那一个。 颜色即判定：绿 OK（同一目标）/ 蓝 NEW（新目标，无历史）/ 橙 SNAP（判为瞬移，滤波与 PID 已被硬重置）/ 红 REJECTED（宽高比离谱被丢掉）。

11. 开镜档（自动开镜期间的第二套瞄准参数）

每个热键现在有两份瞄准控制器参数：ctl_*（默认档，平时生效）与 ctl_scope_*（开镜档，自动开镜生效期间整组取代默认档）。 它不是"又加了 18 个旋钮"，而是同一组 18 个旋钮的第二份取值。

为什么需要它：镜内灵敏度被倍率放大

开镜后游戏对同样的鼠标计数给出更大的画面位移（倍率越高越明显）。 镜前标定好的 ctl_kp_x / ctl_k_px_per_count 直接用在镜内， 等效回路增益等于乘上倍率 —— 表现就是「镜前一甩、进镜就飞」（瞬狙最典型）。 开镜档让镜内用一套独立的（通常更小的）增益与灵敏度折算。

11.1 什么时候切档（判定在 runtime/aim_loop.cpp）

两条同时成立才切：

  1. 该热键开了开镜档：ctl_scope_enabled = 1 （UI：自动扳机 → 自动开镜 → 开镜期间）；
  2. 自动开镜已经按下了右键，且热键仍被按住。 「算不算在镜内」按开镜方式分两种：
    • 长按（mode 2）：右键真的按着才算 —— 用开镜控制器自己的 engaged()。离开命中区会自动收镜，那一刻就切回默认档。
    • 点按（mode 1，不收镜）：那一次点按之后镜头在游戏里一直开着， 所以「在镜内」粘到松开热键为止 —— 不能跟着命中区来回翻， 否则「命中了」和「没命中」会用两套参数，与实机镜头状态对不上。

★ 它跟着「自动开镜」走，不跟着「游戏内开镜」走。 热键本身绑右键时，自动开镜整项不生效（否则会把镜切回去），所以那种情况下开镜档也不会切入 —— 镜头是你自己按的，程序无从判定"现在在镜内"。

★ 相位：读的是上一拍的状态。 开镜判定要用本拍的目标框（命中区），而目标框是控制器算完才有的，所以本拍读不到本拍的判定。 差一拍 ≈ 几毫秒；这样也刻意不去改动扳机 / 开镜的既有相位。

11.3 不随之切档的参数

下列参数仍然只有一份，不随开镜切档 —— 它们管的是「瞄谁 / 怎么走」，不是「用多大力」：

  • 瞄点 Y：ctl_y_offset / ctl_y_offset_max（以及瞄准类别里的逐类 Y）；
  • 选靶与稳定器（全局，见第 8.2 节，界面在 控制 → 稳定器）： target_hysteresis_ratio / target_max_distance_px / target_match_center_ratio / target_area_ratio_tol / target_k_snap_mult / target_min_aspect / target_max_aspect；
  • FOV / 动态 FOV / 瞄准类别 / 轨迹曲线 / 自动扳机（含开镜方式与延时）/ 自动急停。

11.4 一键复制

在「自动扳机 → 自动开镜 → 开镜期间」选「用「开镜独立瞄准参数」那一套」后， 下面那张「开镜独立瞄准参数」卡里可以选一个源热键并点「复制它的默认参数」。

  • 复制方向：源热键的【默认档】 → 本热键的【开镜档】（整套 18 项）。
  • ★ 复制的永远是对方的默认档，不是对方的开镜档。 所以可以先把某个热键在镜内调好当模板，再从别的热键一键搬过来。
  • 源热键选自己 = 把本热键的开镜档重置回自己的默认参数。

11.5 怎么确认它真的切了

切档那一刻会在日志里打一行（只在切换时打，不刷屏）： 

[scope] 自动开镜生效 -> 切到【开镜档】瞄准参数
[scope] 自动开镜结束 -> 切回热键【默认档】瞄准参数

看不到这行，说明没切档：要么开关是「跟随热键」，要么自动开镜根本没按下右键（见 11.1）。

11.6 兼容性与存疑

  • 老配置（没有这些键）⇒ 开关默认 0（跟随热键），而且开镜档那 18 个值就等于默认档的 出厂默认值 —— 所以「打开开关但什么都不改」也不会突然变成另一套参数。 默认状态逐拍与没有这个功能时完全一致。
  • 存疑 镜内最优值没有任何实测依据，本文档给不出建议起点。经验方向是"整体比镜前更保守"， 但具体降多少必须实机试（可先按 11.4 复制一套，再把 ctl_scope_kp_x 整体下调 30~50% 起试）。

12.2 已核实的事实（不是推测）

以下三条已用全仓库 grep + 逐行读码核实
  1. kLoopDeadTimeMs = 46.0 是死代码。 唯一出现处是 pid_controller.h:90 的声明行， 没有任何 .cpp 引用。所以本控制器没有死区补偿 —— 没有 Smith 预估器、没有延迟缓冲、没有事件同步。 46ms 只用于「解释临界增益为何是 0.2602」，不在运行时起作用。 （docs/architecture.html:217 声称 PID「含链路死区补偿（46ms）」，与代码不符。）
  2. stabilityRatio 是死遥测。 每拍每轴都算并存入 AxisTelemetry::stabilityRatio， 但 telemetry() 在生产代码里零调用点 （仅 tests/control_layer_test.cpp 读取）。 UI、日志、IPC 都拿不到它 ⇒ 必须手工按第 3 节公式核算。
  3. Snap 判据的实际阈值是 0.5 个对角线，不是 1.15。 stabilizer.cpp:56-57：不满足 centerDist ≤ lastDiag × matchCenterRatio(0.5) 就判 Snap ⇒ 触发滤波 + PID 硬重置。 小目标（40×80）在 120fps 下只需 ≈45 px/拍 就踩线。 这是「跟枪一顿一顿但参数看不出问题」的头号嫌疑。
  4. kCountsPerPixel 与 kCriticalGain 各自只被使用一次， 都只在 stabilityRatio 内部（pid_controller.cpp:12-13）。 它们不参与实际输出计算 —— 输出用的是 u = dt·Kp·(P+I+Kd·D)，与 0.593 / 0.2602 无关。 所以这两个常数只影响「稳定度读数」，不影响任何实际位移。

12.3 存疑项（源码无依据，请以实机为准）

以下几条源码里没有明确依据，调参时请自行验证
  1. Kp·dt 与实测饱和点不一致。 公式 e_sat = M/(Kp·dt) 在 120fps 下给出 686px， 但实机手感是误差超过约 5.7px 就满量程。 源码与注释都没有解释这个差异。 结论：稳定判据与相对比较可以信公式；绝对饱和点请以实测手感为准。
  2. tauUnwindSec=30ms 与 tauDerivSec=20ms 无实测依据。 UI 原文：「30ms 是历史调整后的起点，无实测依据」。 测试只验证了「比旧的 200ms 快」这个方向，没有验证 30 是最优值。
  3. 稳定器 5 项 + 滞回倍数是占位值。 UI 原文：「目前都是【占位值】，没有实测依据，默认值只保证『程序能跑』。」
  4. α-β 滤波器的 τ=30ms 不可调。 是源码常量 kAnchorFilterTauMs，没有对应配置键。
  5. 实际 dt 没有被记录到任何地方。 没有日志输出 dtSec，所以「你的回路帧率到底是多少」 只能通过外部手段（采集 FPS 读数、或插桩）确定。
  6. 三个常数（46 / 0.2602 / 0.593）没有可查的推导过程。 仓库内没有生成器、没有标定脚本，docs/architecture.html:260 自己也写明 「这些是唯一记录，没有文档依据可查」。 它们与逆向工程文档中 Kp×s_max ≲ 52 的实机结论自洽。
